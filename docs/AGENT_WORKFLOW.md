# 智能体长任务工作法

这套工作法用于跨窗口、长时间或容易中断的实现任务。项目事实写在正式文档里；任务进度写在临时进度文件里，两者不要混用。

OpenAI 官方当前建议长期工作明确写出结果、约束和完成标准，并在同一任务中持续补充上下文。Codex 会在开工前自动读取项目 `AGENTS.md`。本项目据此采用下面的本地协议。

## 1. 三类文件

| 类型 | 文件 | 保存什么 | 不保存什么 |
| --- | --- | --- | --- |
| 项目规则 | `AGENTS.md` | 每个智能体都必须知道的入口、边界、命令 | 完整需求、单次任务流水账 |
| 长期事实 | `docs/*.md` | 已确认的产品、交互、设计和验收 | 当天做到第几步 |
| 任务状态 | 根目录 `PROGRESS.md`、`BLOCKED.md` | 当前目标、证据、下一步、待裁决事项 | 新产品事实、聊天复述 |

## 2. 开始任务

1. 读取 `AGENTS.md`。
2. 按任务阅读 `docs/README.md` 指向的现役文档。
3. 查看 `git status`，识别已有改动，不能把用户改动当垃圾清理。
4. 读取现有 `PROGRESS.md`：如果目标相同就续跑；如果是新目标，保留旧交付证据后重写为新任务。
5. 用 `templates/PROGRESS.md` 和 `templates/BLOCKED.md` 的结构建立任务状态。
6. 先运行基线检查，把真实结果写入进度，再改代码。

一个合格目标必须包含：

- **结果**：用户最终能做到什么，而不是“写若干文件”。
- **约束**：不能碰的路径、不能改变的行为、成本和权限边界。
- **完成标准**：测试、截图、数据恢复或人工复核如何证明完成。

## 3. 执行循环

每一轮只做一个可验收阶段：

```text
读取当前状态 → 选择下一项 → 实现 → 运行对应检查 → 记录证据 → 更新下一步
```

- 每完成一个阶段立即更新 `PROGRESS.md`，不要等到最后凭记忆补写。
- 同一检查连续失败三次时暂停该方向，记录原始错误、已尝试方案和可继续事项。
- 需要用户决定但不阻断其他工作时写入 `BLOCKED.md`，继续不受影响部分。
- 发现文档与代码不一致时，先判断是“目标尚未实现”还是“事实过期”；不得擅自用代码覆盖产品目标。
- 后续消息改变范围时，在进度文件记录变更时间和影响，不默默丢弃已完成工作。

## 4. 中断与续跑

新窗口或上下文压缩后按以下顺序恢复：

1. `AGENTS.md`
2. `PROGRESS.md`
3. `BLOCKED.md`
4. `PROGRESS.md` 中列出的相关正式文档和代码
5. 最近一次验证输出或截图

恢复后先核对代码与进度文件是否一致，再继续“下一步”。已经有证据的完成项不从头重做；若工作区已变化，只重跑相关基线。

## 5. 修改产品决定

执行智能体无权把实现便利变成产品决定。确实需要改变时：

1. 在 `BLOCKED.md` 写清当前决定、冲突证据、两个以上方案和各自代价。
2. 由产品讨论拍板。
3. 先更新 `DECISIONS.md`，再同步 `PRODUCT_SPEC.md`、`UX_FLOWS.md`、`DESIGN_SYSTEM.md` 或 `ACCEPTANCE.md`。
4. 最后修改代码和测试。

同一事实只在一个正式文档详细解释，其他文件用链接或受众专属摘要。

## 6. 交付与验收

交付必须包含：

- 完成了什么，用户现在能做什么。
- 修改的关键文件。
- 实际运行的验证命令及结果，不写“应该通过”。
- 页面任务的截图绝对路径和测试尺寸。
- `BLOCKED.md` 中仍未裁决的问题；没有就写“无”。
- 已知限制和下一步，但不把未完成项包装成完成。
- 本阶段分支、提交 SHA、推送结果和 PR URL（如有）；完成阶段不得只留在本机。

产品与视觉验收由总设计师进行。执行智能体负责提供可复现证据，不给自己做最终审美判定。

阶段结束后从最新 `main` 使用 `codex/stage-<编号>-<主题>` 分支承载下一阶段。当前阶段门禁通过后显式提交并推送；需要独立审计、模型质量评测或视觉终审时先建立或更新 Draft PR，复核通过后再合并。推送前必须再次排除 `.env`、`.novel_*`、审计现场和项目外研究。

## 7. 收尾

- 稳定的新产品决定进入 `docs/`；一次性调试过程留在 git 历史或任务进度，不污染规则文件。
- 根目录任务状态在目标完成并验收后可归档；删除前必须确认其中没有唯一事实。
- 不自动删除旧版本、用户数据、设计探索图、分支或工作树。
- 只有已合并、工作树干净且不含本地数据的阶段分支或 worktree 才能清理；其他情况列为保留项。
- 文档变更也要检查链接和 `git diff`，确保没有新增第二套冲突答案。
