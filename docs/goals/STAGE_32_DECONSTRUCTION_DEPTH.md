# 阶段 32：把作品拆解做到可用、可信、成本可控

> 2026-09-13 现役目标。优先质量达标与简单交付，替代此前要求六视角全部建齐的近期范围。生成、蒸馏和双引擎暂缓；本文件是当前阶段任务来源。

## 唯一目标

作者导入一本小说后，在现有平台看懂主要人物为何作出选择、大剧情怎样相互推动、主要明暗线怎样展开，并能回到正文核对。保留已认可的章节拆解，补足全书综合；不为功能齐全重新搭建整个平台。

## 本版交付什么

| 交付 | 达标要求 |
| --- | --- |
| 人物卡 | 首屏抓住这个人的特点；详情用关键经历解释动机、关系冲突与变化。主要人物写清，配角从简，避免标签和重复堆字。 |
| 全书剧情地图 | 仍以大事件/副本为节点，说明前因后果、人物目标和主要明暗线的联系。 |
| 线索与节奏 | 主要线索说明出现、发展、理解改变、揭晓或未回收；节奏结合剧情解释紧张、舒缓和关系发展，不另造复杂评分系统。 |
| 易用前端 | 现有页面直接显示上述内容，人物详情可进入和返回，重要依据可定位正文。地点先作为剧情中的辅助信息。 |
| 可控分析流程 | 优先复用旧结果；新分析按需读材料、只增加或修正相关内容。过程可续接，费用完整记录，不超预算继续调用。 |

人物相关矛盾与疑问归入人物卡，真相与伏笔问题归入线索，不新增重复栏目。已有双时间线和正文入口保留。地点没有明确依据就留空；“提到某地”不能当作“身在某地”。

## 下一项实际工作

**先交一份同源内容样例，不先重构后端。**

利用已有报告，补读必要原文，整理 1–2 位主要人物、2–3 个相连的大事件、一条覆盖埋设与揭晓的主要线索，以及随剧情出现的节奏说明。涉及地点时顺带展示，不为凑字段补全世界百科。

样例先在对话或现有预览中让用户判断内容。材料不足就明确边界，不能补造完整暗线。只让用户判断内容是否到位，不要求其评审技术报告。

## 研发顺序

1. **样例到位。** 用同一份正文与旧结果对比，修正影响人物理解和主线判断的问题；已有正确章节内容不重拆。
2. **最小集成。** 按通过的样例补必要字段、聚合和页面。沿用现有 API、存储、证据定位、人物 ID 与预算账，不以换框架为任务。
3. **受控试跑。** 将累计报告重发改为新增/修正结果，按任务选取少量旧资料和原文。分别检查内容质量、费用和页面流程；修复会影响使用的实际问题。
4. **整书交付。** 小样与受控试跑通过后，再处理未完成的全书综合；可用旧结果直接复用，只有缺口才补读。浏览器实际打开用户作品检查，并给出入口、范围、成本和剩余问题。

实现过程中先做与改动相关的检查，集成结束运行项目要求的回归与交付检查。不把每次内容调教都扩成新一轮系统审计，也不跳过既有数据安全合同。

## 达标即可停止的验收

- **内容：** 用户认可同源样例；全书抽查覆盖前、中、后段。主要人物的关键选择、主线因果、核心揭晓没有影响理解的事实错误；少量无法确认的解释允许明确标注未知或推断。
- **呈现：** 人物、大剧情、主要线索能够实际浏览，正文引用可以核对；没有妨碍主要流程的页面问题。无需完成所有图表和布局增强。
- **范围：** 正文读取范围与全书综合范围如实标明。全部章节报告齐全但全书未综合，不显示整书交付完成。
- **成本：** 完整计入分段、补读、记忆、综合、结构修复和失败重试。约 70 万字从零首轮完整拆解 ≤10 元是待验证目标，达到预算边界暂停；若无法兼顾质量与预算，交代实测结果再调整方案。
- **交付：** 相关功能检查与最终浏览器体验通过；用户看到真实内容，而非功能清单或空字段。剩余不影响本版目标的增强进入后续清单，本版收口。

不以人物数量、字段数量、图上线条数量、测试总数或自报置信度代替质量判断。成本试验和文学评价分别记录；复用旧分析的补全费用不能冒充从零整书费用。

## 最少的实现约束

- 正文、已认可的章节/卷级报告保留；全书综合作为关联这些材料的派生结果，不覆盖作者正文。
- 相同人物的别名可关联，歧义称呼不强并；后文揭晓可修正推断，读者当时所知不能被结局倒灌。
- 重要判断有正确来源；结构、ID、引用与账户边界由代码校验，文学动机和人物反差由模型结合场景解释。
- 模型任务只取需要的资料，完整人物卡留给作者阅读。当前任务、必要原文和关键事实优先，放不下就缩小任务；不静默裁掉关键约束。
- 旧结果缺新字段时保留已有可读内容，不造假补齐，不为兼容批量改写历史数据。
- 保留既有来源版本、账户隔离、失败保留结果和预算止损；复用已有机制，不建设新的恢复平台。

## 当前不做

独立地点工作区、全量场景数据库、复杂地理地图、图数据库/向量服务迁移、专门上下文编译框架、新 Agent 编排平台、公共语料库、类型蒸馏基础设施、双引擎、生成改写和生产部署均不属于本版。某项机制只有在实际缺口阻碍达标时，才以最小方式单独引入。

六视角是历史探索范围，不再要求六个独立栏目全部建齐。类型蒸馏、双引擎也不再是未来生成的必经步骤。

## 工作与汇报方式

主 Agent 负责范围、集成和自查。简单任务直接完成，只有可独立并行且有必要的任务才考虑分工；不为每个字段开任务。不让用户转发子任务消息或阅读长报告。

每次交付只说明：改好了什么、在哪里看、质量与费用验证到哪一步、还有什么影响使用。涉及内容判断时提供具体前后样例。

继续遵守根目录 AGENTS.md 的安全、回归、分支和交付规则；不删除既有测试或把失败改成通过。提交只含本阶段所属文件，保护既有 dirty worktree；阶段交付的分支、提交、PR 和实际检查结果写入 PROGRESS.md。目标文档更新本身不算功能阶段完成。
