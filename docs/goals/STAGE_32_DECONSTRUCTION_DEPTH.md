## 这阶段为什么做

把阶段 31 的“概览、基础时间线、逐章表、证据回链”升级成真正可供作者学习成熟作品、理解自己作品的深度拆解。正确性与证据可信度优先于维度数量，数据安全优先于速度。

## 当前执行顺序与收口门

阶段 32 的六个视角仍是最终产品范围，但本轮按下面五个门逐步推进。每一门都要保存可复跑证据，未通过前不得跳到下一门。

1. **冻结章节/卷级结果。** 盘点现有拆解的来源范围、稿本版本、证据和状态，保留已经认可的章节结论。只记录明确错误、重复实体、证据错绑和记忆矛盾作为定点修正项，不为填新字段批量重跑。
2. **建立全书聚合层。** 在不改写卷层的前提下，合并跨卷人物身份与变化、主要明线/暗线、事件因果、悬念揭示顺序和节奏关联。聚合结论必须保留来源卷/章节与不确定边界；卷层变化会使受影响的全书结论重新计算。
3. **制作同源小样并确认。** 使用相同正文和冻结结果，交付一个重要人物、一条覆盖出现至揭示或明确未回收的主要线索、两到三个节奏/关系片段的前后对比。小样必须能回答人物选择、事件推动和读者获知变化三个问题，并能点击核对依据。小样未通过，不接入全书新模型运行。
4. **做真实成本试验。** 先在受控范围测量 DeepSeek 的输入、缓存读取、输出、重试和收口调用，记录模型与价格时段。以约 70 万字作品首轮完整拆解不超过 10 元作为待验证目标，预留收口预算和止损线；达到止损线时暂停新调用、保留增量并显示未完成，不自动透支。
5. **全书整合。** 只有小样质量和成本试验都通过，才对当前稿本的所有有效卷执行统一流程。先逐卷完成，再单独进行人物、线索、因果、节奏等全书收口；全书层没有证据的部分标为未知/当前范围未回收，不能用结局信息倒灌读者视角。

### 卷层与全书层合同

- 卷层负责连续章节范围内的事实、事件、人物表现、局部线索、证据和不确定项，正文或范围指纹变化时独立失效和重跑。
- 全书层只引用当前有效卷层，负责跨卷归并和关系展示，不覆盖卷层事实，不把全书推断写回章节结果。
- 同一人物、事件或线索在不同卷出现时使用稳定 ID；合并失败先保留为待确认关系，不能靠名称相同直接覆盖。
- 全书层显示“已读范围、已聚合范围、待处理范围”和费用账，分段完成不能显示为全书完成。

## 交付合同

### 1. 架构与公开 schema

先冻结版本化公开合同。每个分析项至少含稳定 ID、类别、简短结论、来源章节、UTF-16 定位或章节级证据、confidence、uncertainty；关系项还要有起点、终点、关系/因果类型。人物状态、剧情线和伏笔能够按章节或 0–100% 进度回看。结果继续绑定 account、project、active version、revision 和 source hash，沿用七种 canonical 状态与历史只读语义。

### 2. 拆解引擎与后端

按“章节事实提取 → 跨章归并 → 六视角分析 → 证据校验 → 结果发布”实现可恢复流水线。覆盖多主角、多线叙事、倒叙、插叙、空白章、Unicode/emoji 和长篇多章；不能把某套付费节点模板当通用真相。结论没有证据时降低置信或明确未知，不得编造。失败、重试、服务重启、正文修订和历史恢复继续幂等，不回写正文或故事档案。

### 3. 独立创作前端

在现有作品拆解页提供总览和六视角导航；人物关系/剧情因果/伏笔链使用可读的关系视图，节奏和读者体验共用 0–100% 时间轴，文笔技法以观察、例证和可学习说明呈现。点击任一重要结论可打开证据抽屉并定位正确稿本；历史证据只读。空态、排队、运行、失败、过期、待重建和完成均来自服务端，刷新与重登可恢复。1440×900 和 1024×900 不横向溢出，键盘可达，reduced-motion 有效。

### 4. 集成与独立审计

管理任务整合后，由未参与实现的审计任务验证账户隔离、严格 response schema、证据边界、source hash、后台恢复、并发修改、失败重试、历史只读、无正文泄漏及真实浏览器流程。发现 P0/P1/P2/P3 后直接回派原任务修复并复验，全部为 0 才能合并。

## 分工与先后顺序

1. 架构任务只负责 schema、状态机、数据/锁/恢复边界及契约测试；冻结合同后发回管理任务。
2. 引擎/后端任务基于冻结合同实现六视角分析、存储、worker/API 和专项测试，不改 `frontend/**`。
3. 前端任务可在合同冻结后与后端并行，只改 `frontend/**` 和前端合同测试，不伪造服务端状态。
4. 管理任务按“架构 → 后端 → 前端”集成，处理接缝并运行完整门禁。
5. 独立审计最后执行；审计任务只读仓库和隔离数据，不修改业务代码。

## 验收标准

- 六视角均有真实结构化输出；所有重要结论都有至少一条有效 evidence reference，或明确标为不确定，证据定位不得越出来源正文。
- 人物/剧情/伏笔关系 ID 稳定且引用有效；时间线有效正文首点为 0、末点为 100、全程单调；历史稿本证据不会跳到当前同编号章节。
- 至少用单章、普通多章、多线/非线性、100 章合成长篇、前导空白及 emoji/UTF-16 六类授权或合成样本验证；不得提交受版权保护原文。
- 修改正文后旧结果进入 stale/rebuild_required；重建、失败重试、服务重启和重复请求均不产生重复结果或覆盖作者正文。
- 匿名 401、跨账户 404；公开 API/DOM 不含 account_id、正文副本、prompt、raw completion、private_memory、内部错误或密钥。
- 基线不得回退：测试总数不低于 135，failed=0、skipped=0；compileall、`node --check frontend/app.js`、`git diff --check` 通过；OpenAPI 不少于 58/61，旧 `/novel` 保持 16/19。
- Windows 与 Ubuntu CI 通过；真实 Windows 浏览器走通导入/已有作品 → 后台拆解 → 六视角 → 证据 → 刷新/重登 → 修改后重建，1440/1024 控制台无 error/warn。
- 禁止通过 skip/todo、放宽断言、mock 被测核心、删测试、吞异常、静态假数据或修改验收阈值制造通过。

### 阶段 32B 客户验收

客户验收针对同一份正文的可读结果，不以字段数量替代质量判断：

- 人物卡能说明重要人物的核心追求、顾虑、不同处境下的多面性、内在/关系冲突、关键选择和变化，并以章节证据支撑；人物相关疑问归入人物卡，分析错误不包装成文学矛盾。
- 全书地图能说明事件之间的因果、明线与主要暗线如何交汇；每条主要线索尽量呈现首次出现、后续展开、读者理解变化、揭示/未回收状态和全书作用，并区分故事事实、人物所知和读者当时所知。
- 节奏分析按实际段落说明紧张、舒缓、高潮、余波、日常、幽默和关系段落的作用，并能回到剧情节点；不使用没有正文依据的固定高潮间隔或“科学注意力曲线”。
- 作者可从人物、事件或线索结论定位正确稿本和章节依据；结论材料不足时显示不确定/当前范围未回收，不能显示为确定事实。
- 页面同时显示卷层结果与全书聚合状态，正文变化后不会继续显示旧的全书结论；部分完成、成本达到止损线或收口失败时清楚显示未完成原因。
- 交付样例必须包含逐项修改清单、同源前后对比、直接体验入口和验证范围；真实分析质量、功能检查、浏览器体验和未完成事项分开报告。

### 成本与完成门

- 10 元仅为待验证目标，成本试验必须产生可复核的真实用量账；不能用缓存命中比例、测试假数据或一次局部运行推断全书成本。
- 费用预算覆盖卷级分析、全书聚合和合理重试；开发调试与人工评审另列。请求前检查预计剩余预算，达到止损线时保留已完成结果并暂停后续调用。
- 全书完成必须同时满足来源范围完整、全书聚合已收口、主要人物/线索/节奏结论可核对、未确定项有边界和费用账完整；分段报告齐全但没有全书收口不算完成。
