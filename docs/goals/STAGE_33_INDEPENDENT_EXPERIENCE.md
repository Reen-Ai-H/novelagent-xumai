# 阶段 33 任务书：独立创作体验收口

这是阶段 32 合并后的独立创作体验合同，也是阶段 33 实现与验收的唯一入口。中断或更换会话时，先读 `AGENTS.md`、本文、`PROGRESS.md`、`BLOCKED.md` 和 `docs/README.md`，再从真实证据继续，不按聊天记录猜测范围。

状态：待实施合同。本文和相关决定已经完成合同复核，不代表功能已经修复，也不代表独立审计已经通过。

基线：GitHub `main=ec2f31a`，阶段 32 候选已合并；基线为 204 tests、0 failed、0 skipped，OpenAPI 58 paths / 61 operations，旧 `/novel` 16 paths / 19 operations。阶段 33 只收口独立创作的编辑、档案、版本和拆解入口体验，不回退阶段 32 的数据、证据和安全合同。

## 1. 为什么做这阶段

管理任务已在隔离真实浏览器中复核作者主流程，确认以下四个阻力。它们都发生在真实服务端数据已经存在时，不能用静态页面或前端假数据掩盖。

| 编号 | 已确认摩擦 | 当前合同根因 | 收口结果 |
| --- | --- | --- | --- |
| F33-01 | 新建章节后仍停在旧章 | `POST /chapters` 返回新章，但前端保留旧的 `activeChapterId`，重新读取后又按旧选择渲染 | 创建成功后立即进入服务端返回的新章，标题、正文输入区、目录选中态和 URL 一致 |
| F33-02 | 已选第二章，刷新后回到第一章 | 选中章只存在 JavaScript 内存；刷新重新加载时没有可恢复的导航目标 | 选中章成为可恢复的编辑导航状态，刷新、深链和重登保持同一当前稿本章节 |
| F33-03 | 从档案返回时，已落盘但未完成的章节显示“等待保存” | `drafting` 同时被当作“正文未落盘”和“本章尚未完成”，`status` 没有和保存状态分开 | 已落盘和本章完成是两条独立状态；已保存草稿显示“已保存，尚未完成本章”，不能再误报“等待保存” |
| F33-04 | 版本预览只展示第一章摘要 | API 已返回稿本章节，但前端只取 `firstChapter` 的 260 字片段 | 预览能确认完整恢复目标，至少可检查稿本元数据、全部章节清单和每章只读正文，不再只展示第一章 |

四个问题属于同一个闭环：作者创建或选择章节，正文可靠落盘，章末状态可理解，离开档案后能回到正确编辑位置，恢复版本前能确认目标。任何实现都必须同时验证服务端持久数据和浏览器呈现。

## 2. 目标与非目标

### 2.1 本阶段目标

- 让新章创建成为一个明确的“创建并进入新章”动作，不产生幽灵章节，也不因重复点击失控增长。
- 让当前编辑章成为可恢复的 URL 导航状态；服务端仍是正文、稿本、revision 和任务的唯一真相。
- 把本地传输状态、正文是否已落盘和章节分析/完成状态分开表达。
- 让档案与正文之间的跳转保持当前稿本、当前章节和只读边界，不丢已保存草稿。
- 让历史版本预览足以确认恢复对象，并在恢复时继续使用“创建新的当前稿本”合同。
- 继承阶段 31/32 的账户隔离、作者 revision 门禁、后台恢复、拆解 source token、证据只读和唯一正式正文约束。

### 2.2 非目标

- 不新增独立创作之外的产品入口，不改 AI 创作室、AI 导演台或模式转换。
- 不改阶段 32 六视角分析语义、报告 schema、证据算法、稳定 ID、拆解锁顺序或模型运行时。
- 不在独立创作中加入 AI 续写、改写、扩写、代写、标题生成或自动润色。
- 不建设分享、公开发布、多人协作、云同步、正式支付、管理员、生产部署或原生移动端。
- 不维护平行正文分支。历史稿本仍按既有 30 天恢复区保留；恢复仍创建新的当前稿本，不原地覆盖历史。
- 不把选中的章节、预览展开态或筛选状态写进 `.novel_*`。这些是可重建的界面导航状态，不是作品事实。
- 不用模型为版本生成摘要，不用静态 fixture 冒充真实正文，也不借阶段 33 重新打开阶段 32 已通过的语义争议。

## 3. 现有边界与术语

阶段 33 沿用现有对象，不另造一套正文或档案模型。

| 对象 | 本阶段语义 |
| --- | --- |
| `ChapterDocument.content` | 当前稿本中作者正在编辑的正文。读取 workspace 得到的内容已经由服务端落盘。 |
| `formal_content` | 本章最近一次完成并进入正式分析的正文。它不等于当前草稿。 |
| `server_revision` | 作者正文保存的服务端 revision。它是保存并发门禁，不是分析任务状态。 |
| `ChapterDocument.status` | `drafting`、`analyzing`、`ready`、`failed` 的章节完成/分析生命周期，不单独代表“是否保存”。 |
| `activeChapterId` | 当前页面编辑目标。阶段 33 仍可在内存中使用它，但必须由 URL 恢复，并以当前 active version 的章节为范围。 |
| `pending_changes` | 已落盘的旧章修改批次，等待作者选择忽略或全文重建。它不能被“保存状态”文案吞掉。 |
| `read_only` | 档案快照和历史稿本预览的只读边界。只读内容不能回写正文、档案或当前稿本。 |

作品、稿本、章节、档案快照、拆解报告和后台任务继续绑定账户和作品，不因本阶段新增界面导航而改变身份。

## 4. 四项体验合同

### 4.1 F33-01：新建章节后立即进入新章

#### 用户可见结果

1. 作者在当前稿本点击“＋ 新章”。若当前正文有本地未保存输入，先完成一次保存；保存失败或存在冲突时停留在原章，并明确说明原因。
2. 创建请求成功后，以响应中的 `chapter.chapter_id` 为唯一选中目标，不猜测章节号，也不重新取第一章作为默认。
3. 目录中新章出现选中态，章节标题、标题输入框、正文输入框、字数、revision 和“完成本章”按钮全部对应新章。
4. 新章为空且尚未保存时，可以显示“等待保存”；该文案只适用于没有已落盘正文的空白章。
5. 标题输入框或正文输入框获得一次明确的焦点，焦点变化可被键盘用户和辅助技术感知，不依赖颜色或动画证明已经切章。
6. 请求失败、会话失效、账户越权或项目模式不匹配时，不改变当前选中章，不更新 URL，不显示“新章已加入”的成功通知。

#### 接口与幂等边界

- 继续使用 `POST /api/independent/projects/{project_id}/chapters`。成功响应中的 `chapter` 是服务端创建的完整章节对象，至少包含 `chapter_id`、`chapter_number`、`title`、`server_revision` 和 `status`。
- 前端必须对创建动作做 single-flight 保护。一次点击只能有一个在途创建请求，按钮在响应或失败前禁用。
- 网络超时不得由客户端无条件重发一个没有幂等身份的创建请求。若实现任务为该接口增加幂等键，键必须以作品和当前稿本为作用域，重复请求返回同一新章且不增加章节数；幂等键不得回显到公开响应。
- 创建章节本身不触发本章分析，不改变既有档案快照，不改变阶段 32 拆解报告；只有作者保存并点击“完成本章”才进入既有后台分析合同。

#### 验收断言

- 服务端返回的新 `chapter_id` 最终等于目录选中项、编辑器绑定项和 URL 中的章节 token。
- 新章内容为空时，旧章正文、revision、formal content、档案和拆解侧车均保持不变。
- 双击、快速连按和一次可重试的浏览器事件不会产生两个新章。

### 4.2 F33-02：选中章节可通过刷新恢复

#### 规范 URL

独立编辑器使用以下可分享、可重建的导航形状：

```text
/independent/{project_id}?chapter={chapter_id}
```

其中 `chapter` 是当前 active manuscript version 内的 `chapter_id`，必须进行 URL 编码。`view=deconstruction` 仍然是作品拆解入口；不得把拆解状态或正文内容塞进编辑器 query。

#### 选择与恢复规则

- 首次打开没有 `chapter` 时，选择当前稿本的第一章，并用 `replaceState` 补齐规范 URL。
- 选择另一章前，先处理当前章的本地缓冲。保存成功才切换；保存冲突、保存失败或作者取消处理时，保留原章、原 URL 和本地草稿。
- 选择成功后，目录选中态、标题、正文、revision、完成按钮和 `?chapter=` 必须同一批更新。选择本身不创建版本、不触发分析、不写本地作品数据。
- 刷新、重登、从书架深链重新进入时，先读取服务端 workspace，再在当前 active version 中解析 `chapter`。有效 token 必须恢复同一章，不得无条件回到第一章。
- 如果 token 不属于当前 active version，不能假装恢复成功。可在安全默认下打开第一章或同章节号的当前章节，但必须显示可读提示并用 `replaceState` 修正 URL，说明稿本已经变化或目标章节不存在。
- 从档案返回正文时，始终打开当前 active version。若档案是历史快照，历史快照保持只读；可以按同一章节号定位当前稿本，但必须明确显示“当前稿本”，不能把历史快照当作可编辑正文。
- 浏览器前进/后退触发路由恢复时，仍按同一解析规则处理；不得依赖上一次 JavaScript 进程的 `state.activeChapterId` 才能正确显示。

#### 版本切换规则

历史恢复会创建新的 active version，章节 ID 也可能随复制而变化。恢复成功后，客户端不得继续使用旧稿本的 chapter token。应按恢复目标的章节号映射到新 active version，并把新的章节 ID 写入 URL；若没有对应章节，明确回到第一章并提示原因。

### 4.3 F33-03：保存状态和完成状态分开

#### 状态来源

- `保存中`、`保存失败`、`保存冲突`、`本地缓冲` 是当前浏览器传输状态。
- 服务器返回 workspace 后，正文已经落盘。客户端应以 `server_revision` 和返回的 `content/title` 为保存事实，并以 `ChapterDocument.status`、`formal_content` 和任务状态表达完成/分析事实。
- `status=drafting` 只能说明本章尚未进入最近一次正式分析，不能推出正文尚未保存。
- `pending_changes` 是旧章修改确认状态，与“已保存”并不冲突；已保存的待确认修改必须继续显示待确认，不得显示成丢失或未保存。

建议使用下表作为公开文案合同。实现可以在视觉上缩短文案，但辅助技术可访问名称必须保留同一语义。

| 服务端事实 | 保存文案 | 完成/分析文案或动作 |
| --- | --- | --- |
| `server_revision=0`、正文为空、`status=drafting` | `等待保存` | `完成本章` 禁用 |
| `server_revision>=1`、正文已落盘、`status=drafting` | `已保存` | `尚未完成本章`；正文非空时允许点击“完成本章” |
| `server_revision>=1`、正文已落盘、`status=analyzing` | `已保存` | `后台分析中`；不得显示为未保存 |
| `status=ready` | `已保存` | `本章已完成，档案已更新` |
| `status=failed` 且正文仍在服务端 | `已保存` | `分析失败，可重试`；不得丢正文 |
| 本地输入尚未成功提交 | `本地缓冲` / `保存中` / `保存失败` / `保存冲突` | 依据保存结果决定是否允许完成 |

特别地，作者主动保存空正文时 `server_revision` 也可能大于 0。此时不能显示“等待保存”，应显示“已保存，正文为空”，并禁用“完成本章”。

从故事档案返回编辑器时必须重新读取真实 workspace 或使用同一份刚刚读取的服务端响应，不得用旧的 `state.editorBuffer` 或 `status` 单字段覆盖保存事实。阶段 33 的浏览器验收将专门构造“已保存、未完成、非空正文”的章节，断言页面不出现 `等待保存`。

### 4.4 F33-04：版本预览足以确认恢复目标

#### 预览内容

继续使用 `GET /api/independent/projects/{project_id}/versions/{version_id}/preview`，保持 owner 校验和现有 `read_only` 语义。预览是只读投影，不创建任务，不触发重建，不改变 `active_version_id`，也不修改历史稿本。

预览页面至少同时提供以下信息：

- 稿本标签、版本 ID 的可读短标识、创建时间、当前/历史状态、可恢复截止时间。
- 章节总数、总字数、第一章和最后一章的章节号，避免只靠一段正文猜测目标。
- 按 `chapter_number` 升序列出全部章节。每项至少显示章节号、标题、字数、完成/分析状态和一个来自该章真实正文的有界只读预览。
- 每一章都能展开或选中查看完整的只读正文，或者在服务端采用分页时通过明确的章节读取动作查看同等内容。不能只渲染 `firstChapter`，不能只给整本书第一章的摘要。
- 当前正在查看的章节、稿本标签和“历史正文不会被改写”提示必须在视觉和辅助技术树中可识别。
- 恢复按钮必须带出目标稿本标签、章节总数和“恢复会创建新的当前稿本”的说明。恢复是明确动作，不能因点击预览卡片或键盘焦点落在按钮上就触发。

预览不调用模型，不生成推断摘要。正文片段必须经过 HTML 转义，作者正文中的标记、脚本样式和长标题不能改变预览结构。

#### 恢复安全

- 有本地未保存输入、保存请求在途或保存冲突时，恢复动作必须先保存成功或明确阻止；不能让一次恢复静默丢掉本地草稿。
- `pending_changes` 尚未由作者选择时，恢复动作应阻止并引导先处理待确认修改，或在同等强度的确认流程中明确说明该批次的保留位置。不得静默把待确认批次从界面和服务端状态抹掉。
- 恢复历史稿本后，旧历史稿本的章节、正文、快照、创建时间和恢复期限保持不变；旧 active version 按既有规则进入恢复区。
- 恢复必须在同一 `project_id` 内创建新的 active version，保持恰好一个 active version。新版本的章节内容来自选定历史稿本，而不是当前编辑器缓冲或第一章摘要。
- 恢复成功后，当前页面切换到新 active version，并按恢复目标的章节号重新解析章节；历史预览关闭或保持只读，不能继续把旧稿本当作可编辑目标。
- 过期版本仍可预览历史记录，但恢复返回既有 `version_expired` 安全错误，不删除历史数据。

## 5. 端到端状态与数据流

```text
编辑器 URL/内存选择
        │ 解析当前稿本 chapter_id
        ▼
服务端 workspace ──保存 draft──▶ server_revision + content/title
        │                                  │
        │                                  └─ status=drafting：已保存，尚未完成本章
        │
        ├─ 完成本章 ─▶ formal_content + task ─▶ 分析/档案/拆解 outbox
        │
        ├─ 故事档案只读 ─▶ 返回当前 active version 的编辑器
        │
        └─ 版本预览只读 ─▶ 明确恢复 ─▶ 新 active version ─▶ 新 chapter_id/URL
```

实现必须保证以下不变量：

1. 浏览器显示的正文、标题和 revision 能回到最近一次服务端保存；失败请求不得用乐观 UI 假装成功。
2. 章节选择和预览展开是导航状态，不会改变正文、档案、拆解报告、任务、通知或积分流水。
3. 新章、保存、完成、恢复和重试的重复请求不会产生重复章节、重复稿本、重复任务、重复快照或重复扣分。
4. 任何旧分析或旧稿本都不能覆盖作者较新的正文 revision；阶段 32 的 source version/revision/hash 和 CAS 合同继续有效。
5. 历史稿本和历史档案快照只读。恢复是追加新的当前稿本，不是 JSON 原地覆盖或删除历史。
6. 所有公开响应继续先鉴权，再按 `account_id + project_id + mode` 做归属检查；跨账户仍按既有 404/401 合同返回。

## 6. 可访问性合同

- 章节目录使用真实按钮或等价可聚焦控件，当前项提供 `aria-current` 或等价语义；章节号、标题、保存/完成状态在可访问名称中可读。
- 新章创建后焦点有确定落点；切章、刷新、档案返回和恢复后不能把焦点留在已移除的节点，也不能用自动滚动代替焦点管理。
- 保存状态和错误状态位于 `aria-live="polite"` 或等价区域；“已保存”和“尚未完成本章”不能只用颜色、图标或动画表达。
- 版本预览章节清单、展开控件、只读正文和恢复动作全部可用键盘完成。预览和恢复的 `dialog` 具有可读标题，打开后焦点进入对话框，关闭后回到触发控件。
- `Esc`、Tab、Enter/Space 和必要的方向键行为不与正文输入冲突；正文 textarea 内的方向键仍由编辑器接收。
- `:focus-visible` 必须可见；颜色对比、长中文标题换行、错误文案和状态文字在不依赖色觉时仍可理解。
- `prefers-reduced-motion: reduce` 下，导航、对话框和状态更新不依赖平滑滚动、闪烁或延时动画；所有信息即时可见。
- 不把账户字段、完整内部错误、prompt、私有记忆或非必要正文副本塞入辅助技术树、`data-*` 属性或浏览器存储。

## 7. 响应式与布局合同

阶段 33 至少在 CSS viewport `1440×900` 和 `1024×900` 各走完四个摩擦场景；这两个尺寸的页面根节点不得出现非必要横向溢出，`scrollWidth` 不得大于 `clientWidth`。表格或长正文若需要横向查看，只能存在有明确标签的局部滚动容器，不能把整个工作区推出视口。

- 1440 宽度保留 A 版书脊导航、章节栏、正文列和档案摘要的层级；版本预览对话框内的章节清单和正文区域不会被遮挡。
- 1024 宽度下章节栏、正文和档案摘要允许收窄、折叠或按顺序排列，但“新章”、章节选择、保存状态、完成本章、档案返回和版本预览仍可直接操作。
- 章节标题、版本标签、错误信息和作者正文不得因 `white-space: nowrap` 把页面撑宽；长正文在只读预览中按段落换行。
- 缩放到浏览器默认 200% 或使用键盘完成核心动作时，不得通过 `overflow: hidden` 隐藏操作或正文；焦点落点始终在可视区域内。
- 截图只是辅助证据。布局门禁必须同时记录 viewport、页面 scrollWidth/clientWidth、控制台 error/warn 和实际操作路径，不能裁切截图冒充目标尺寸。

## 8. 恢复、失败和隐私边界

### 8.1 浏览器恢复

- 刷新或重登编辑器时，先恢复 HttpOnly 会话，再读取 workspace 和 URL chapter token；不得依赖 localStorage、sessionStorage 或缓存的完整正文。
- 页面离开、`pagehide`、`visibilitychange` 和路由跳转沿用现有保存门禁。尚未保存时尝试保存；无法保存则警告并留在原章或阻止离开。
- 从档案、拆解和版本入口返回正文，读取统一的当前 workspace。历史快照/历史稿本的内容不能被注入为可编辑当前状态。

### 8.2 服务端恢复

- 阶段 31/32 的章节分析、拆解 outbox、worker、失败重试、source token 和 CAS 规则不因前端导航改变。
- 旧任务、旧报告和旧稿本在刷新时仍能按既有状态恢复；阶段 33 不增加一个只在浏览器存在的分析任务。
- 任何实现变更都不得读写、删除、迁移或批量改写 `.novel_accounts`、`.novel_ai`、`.novel_independent`、`.novel_projects`、`.novel_memory`、`.novel_transactions` 或 `.novel_deconstruction` 中的真实本地数据。
- 文档和测试使用临时隔离 store、确定性 fake 运行时和作者自有/合成正文；不读取 `.env`，不调用真实模型、图片、付费服务或外部账户。

### 8.3 安全公开面

- 版本预览只允许作品 owner 读取。匿名请求返回 401，已登录跨账户请求返回既有 404，不通过错误差异泄露版本存在性。
- 预览正文、章节标题、通知和错误信息全部按文本转义；不得把作者内容拼成可执行 HTML。
- 不公开幂等键、锁 owner、内部 record revision、栈信息、prompt、raw completion、私有记忆、密钥或不必要的账户字段。
- 预览可读取作者自己的历史正文，但不新增“导出”“分享”或面向第三方的正文通道；不把历史正文复制到浏览器持久存储。

### 9.3 真实浏览器流程

由未参与实现的管理/审计任务在隔离真实服务上执行，至少使用 Edge 152 或当前 Windows CI 允许的真实浏览器，在 `1440×900`、`1024×900` 两个 CSS viewport 分别记录操作结果。

1. 登录并新建独立作品，从空白开始；编辑并保存第一章，点击“＋ 新章”，断言页面立即进入新章，输入独特正文后刷新仍是新章。
2. 创建/导入至少两章，选中第二章，记录 URL 和正文标记；刷新、退出重登、从书架深链进入，断言仍为第二章，不能回第一章。
3. 保存一段非空正文但不点“完成本章”，进入故事档案再返回正文；断言正文逐字存在、revision 不回退、保存区显示已保存/尚未完成，页面不出现“等待保存”。
4. 构造至少三章的历史版本，每章使用不同标题和正文标记；打开版本记录，断言所有章节清单和可查看正文均可见，切换到末章仍能确认目标；确认恢复后断言新当前稿本内容与目标一致、旧稿本仍可预览且只读。
5. 在每个尺寸检查键盘完成新章、切章、档案返回、版本预览和恢复；检查焦点可见、aria 状态可读、reduced-motion 不影响信息；记录根 `scrollWidth/clientWidth`、控制台 error/warn、是否有遮挡或整页横向滚动。

### 9.4 反向与回归测试

- 保存失败、保存冲突、创建失败、会话过期、跨账户、空正文、分析失败、历史版本过期和恢复冲突都必须显示安全且可操作的状态。
- 预览只读反向测试：点击/键盘操作预览正文不能修改当前 textarea、档案、版本或任务；历史证据不能跳入错误稿本。
- 选中章 token 无效、当前稿本刚切换、章节号缺失或章节顺序异常时，不得静默把历史正文当当前正文；必须安全降级并提示。
- 保留阶段 32 的六视角、证据、source hash、历史只读、账户隔离和自然正文门禁；不因新增阶段 33 测试删除、弱化或 skip 既有测试。

## 10. 反作弊与独立审计门槛

### 10.1 禁止的通过方式

- 禁止用 `skip`、`todo`、宽松断言、吞异常、静态 HTML、内置正文、前端 fixture、mock 被测核心或只断言字符串出现来制造通过。
- 禁止把章节选择写进 localStorage/sessionStorage 或用浏览器缓存的完整正文掩盖服务端刷新失败。
- 禁止预览只展示第一章却用版本总字数文案宣称“可恢复”；禁止用自动生成摘要替代每章真实可核对内容。
- 禁止把 `drafting` 改名为“已完成”来绕过未完成章；也禁止把已保存草稿写成“等待保存”来隐藏状态合同。
- 禁止改低 204 tests、0 failed、0 skipped、OpenAPI 58/61、旧 `/novel` 16/19 或浏览器尺寸/控制台门槛；不得删除既有测试或受保护数据。
- 禁止读取、输出、提交 `.env` 真实值，触碰或改写 `.novel_*` 真实数据，提交浏览器现场、审计证据或用户正文。

### 10.2 独立审计要求

- 审计任务必须从阶段 33 集成候选的干净提交运行，不得是实现该缺陷的同一任务；审计只读代码和隔离临时数据，不在业务代码中自改自验。
- 审计必须同时比对 API 持久响应、刷新后的 UI、浏览器 URL、版本记录和正文标记。截图只作补充，不能替代逐项断言。
- 审计报告至少给出四个摩擦场景的复现/修复结果、每个 viewport 的控制台和溢出结果、protected-file manifest、测试命令与真实退出码。
- 任一 P0/P1/P2 均不允许合并；P3 不能有未分派、未解释或会掩盖数据/体验回退的问题。失败项回原实现任务修复，再由同一独立审计任务复验。

### 10.3 阶段通过门槛

- 专项 API、前端和浏览器测试全部通过；全量测试不少于 204，failed=0、skipped=0。
- `compileall`、`node --check frontend/app.js`、`git diff --check` 和文档本地链接检查通过；OpenAPI 不低于 58 paths / 61 operations，旧 `/novel` 保持 16/19。

- 作者正文、历史稿本、档案快照、拆解报告、revision/hash、任务和账户隔离均有服务端证据；没有因体验修复回退阶段 32 既有合同。
- 文档、实现和测试的范围与非目标同步；阶段分支已提交、推送、建立 Draft PR，独立审计通过后才能转 Ready 并合并 `main`。合同复核分支本身不宣布阶段通过。
