# 阶段 33 任务书：独立创作体验收口

这是阶段 33 总管理、实现和独立审计的共同合同。中断或换任务先读 `AGENTS.md`、本文件、`PROGRESS.md` 和 `BLOCKED.md`，以最新 GitHub `main` 为基线，不依赖聊天记录补范围。

## 这阶段为什么做

阶段 32 已把作品拆解升级为可回证据的六视角报告，但真实作者从写正文到完成章节，再往返档案、版本和拆解时仍有连续性摩擦。阶段 33 不扩张功能面，只让现有能力成为一条不会丢失写作位置、不会误报保存状态、不会误恢复稿本的连续作者流程。

## 已复现基线

管理任务在 Windows 隔离浏览器服务中使用临时账户和自有合成正文实走了新建、空白写作、自动保存、完成本章、新章、档案、版本、旧章重建和拆解，确认以下问题：

1. 新建第二章后仍停留在第一章，需要作者再次寻找并点击新章。
2. 正在写第二章时刷新页面，会回到第一章；URL 没有承载当前章节。
3. 已按 revision 落盘的未完成章节从档案返回时显示“等待保存”，保存状态和分析状态混在一起。
4. 稿本版本预览只显示第一章前 260 字，无法充分判断整本恢复目标；恢复按钮没有独立确认步骤。

这些证据只来自临时测试数据，不代表可读取或迁移真实作者作品。

## 范围和非目标

- 范围是独立创作的正文编辑、章节完成、故事档案、版本记录、作品拆解五个现役表面之间的连续性、状态真实性、键盘操作、响应式和失败恢复。
- 不重做视觉风格，不新增首页路径，不修改 AI 创作室或导演台，不增加正文建议、续写或改写。
- 不新增分享、发布、多人协作、云同步、支付、管理员、生产部署或公共语料处理。
- 默认只使用现有 workspace、chapter、version、archive 和 deconstruction API。不能为了前端方便把正文副本、账户字段、内部任务信息或密钥加入响应。

## 冻结交互合同

### 1. 章节定位与导航

- 编辑器 URL 使用 `chapter=<chapter_id>` 表达当前章节；作品拆解继续使用 `view=deconstruction`，两者可同时存在且查询顺序不影响解析。
- 有效 `chapter` 优先；无效参数不得报 500 或展示别章正文，回退到编号最大的未完成章节；若所有章节已完成，回退到最后一章。
- 点击章节时用 history replace 更新 URL，不产生无意义的返回栈；新建章节成功后自动选中新章、更新 URL、聚焦标题，并且不会改变已有章节正文。
- 进入档案、拆解或版本流程前先完成当前自动保存；保存失败或冲突时留在正文并保留本地缓冲。往返、刷新和重登回到同一有效章节；目标章节成为历史稿本后按上述安全规则回退。

### 2. 保存、完成与下一章

- 状态至少区分本地待保存、保存中、已保存、保存失败和保存冲突；`server_revision` 已确认且没有本地改动时显示“已保存”，与 `chapter.status` 的分析状态无关。
- 完成本章必须先 flush 当前标题和正文，再按当前 revision 提交。运行中禁止重复提交；超时提示作者可离开，刷新后读取服务端任务继续恢复。
- 完成成功后该章节保持可读；原“完成本章”不再重复可用，主操作变为“新建下一章”。旧章被作者修改后才恢复“完成本章”，并继续进入现有 `pending_changes` 安全流程。

### 3. 档案与拆解衔接

- 正文侧栏摘要、完整故事档案和六视角拆解都只显示服务端状态。切换表面不能清空作者写作位置，也不能跳过保存失败或 revision 冲突。
- 旧章修改提示明确区分“忽略轻微修改”和“按当前全文重建”。重建文案同时说明故事档案与作品拆解会更新，旧稿本和旧拆解历史保持只读。
- 拆解当前证据仍可精确定位，历史证据仍只读；从证据返回正文时把证据所属当前章节写入 URL。历史证据不能借该机制跳到当前同编号章节。

### 4. 版本预览与恢复

- 版本列表保留当前/历史、章节数、字数和创建时间。点击预览后显示该稿本的完整章节目录，可逐章查看标题、完整正文或明确的安全可滚动正文视图，不能只展示第一章摘要。
- 历史版本恢复必须先预览，再打开包含目标稿本名称、章节数和“创建新的当前稿本”含义的确认步骤；取消不发请求，重复点击不创建多个版本。
- 恢复完成后关闭对话框、加载新当前稿本、按章节回退规则定位正文；旧版本、旧档案快照和旧拆解证据继续只读，正文不就地覆盖。

### 5. 可访问性与响应式

- 新焦点有确定去向：新章到标题，版本预览到预览标题，恢复确认到确认标题，关闭对话框回到触发按钮。
- 对话框支持 Escape、Tab 焦点约束和键盘按钮；状态变化使用现有 live region，不用仅靠颜色表达。
- 1440×900 与 1024×900 不产生整页横向溢出；章节目录、正文、档案摘要和版本正文各自在必要时滚动。`prefers-reduced-motion` 继续有效。

## 分工和实现顺序

1. 合同任务只审查本文件、产品决定、规格、流程和验收，不改业务实现。
2. 前端任务负责 `frontend/**`、前端合同测试和阶段 33 浏览器脚本，实现 URL 章节定位、下一章、真实保存标签、完整版本预览与恢复确认。
3. 后端任务只做黑盒安全复核和现有 API 回归；若现有响应足够则不改实现。若发现必须扩展，先回管理任务更新本合同，再改 `app/**`、`schemas/**` 和后端测试。
4. 管理任务集成、处理接缝、跑完整门禁与真实 Windows 浏览器。
5. 未参与实现的独立审计任务最后验证；缺陷回派原实现任务修复，再由同一审计任务复验。

## 自动与真实浏览器验收

- 自动测试必须覆盖有效/无效/缺失 `chapter`、查询参数组合、新章自动选中、刷新/重登、跨表面往返、保存失败、revision 冲突、完成中刷新、重复完成、旧章修改、重建、版本预览逐章、恢复取消/确认/重复点击。
- 黑盒断言作者正文逐字不变，旧版本只读，恢复只新增当前版本，不删除历史；匿名 401、跨账户 404 和现有 owner/mode 门禁不回退。
- 真实 Windows 浏览器至少走通空白作品两章写作、刷新续写、完成章末、档案/拆解往返、旧章修改重建、逐章版本预览、取消恢复、确认恢复和历史证据只读；1440×900 与 1024×900 控制台 error/warn 为 0。
- 全量测试不得少于阶段 32 的 204 项，failed=0、skipped=0；OpenAPI 不少于 58 paths / 61 operations，旧 `/novel` 保持 16/19；compileall、`node --check frontend/app.js`、浏览器脚本语法和 `git diff --check` 均通过。
- 禁止 skip/todo、放宽断言、mock 被测核心、静态假 DOM、吞异常、删测试或修改阈值制造通过。浏览器测试使用真实 app/worker、临时目录、真实会话和合成正文，显式禁止模型与付费请求。

## 完成条件

合同范围全部有可复跑证据；独立审计 P0/P1/P2 均为 0，P3 也记录清零；现役规格、流程、验收、架构、用户说明、进度和阻塞同步；阶段分支提交并推送，Draft PR 的 Windows/Ubuntu CI 对最终 SHA 通过后转 Ready 并合并 GitHub `main`。没有进入 `main` 不算完成。
