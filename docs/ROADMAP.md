## 阶段 32 当前研发顺序

阶段 32 的长期目标仍包含六个相互关联的拆解视角，但当前执行拆成五个可验收门：

1. 冻结已认可的章节/卷级拆解，建立来源、版本、证据和待修正清单。
2. 在卷层之上建立独立的全书聚合层，处理跨卷人物弧、明暗线、事件因果、悬念揭示和阅读节奏；不覆盖卷层事实。
3. 使用同一份正文做小样确认，至少检查一个人物、一条完整线索和两到三个节奏/关系片段。
4. 在受控范围内做 DeepSeek 真实成本试验，测量分段分析、全书收口和合理重试；10 元是待验证目标，设预算止损并保留部分结果。
5. 小样质量与成本都通过后，才执行当前稿本的全书整合，并按客户标准报告完成人物、事件推动和阅读节奏的核对结果。

分段完成、卷级结果齐全或页面能打开，都不代表全书完成。全书完成还需要主要人物跨卷变化、核心线索揭示过程、事件因果和节奏关联完成收口，并有完整费用账。

## 为什么不能跳序

深度拆解先建立对人物、剧情、节奏和语言的可验证表示；本轮还必须先用同源小样证明跨卷聚合方式和真实费用，再扩大到全书。类型蒸馏再复用同一表示从多部作品归纳规律；双质量引擎在离线评测证明有效后，才接入 AI 辅助写作。若直接先改生成提示词，只会得到难以解释、无法回归、容易过拟合个别作品的临时效果。

## 每阶段共同流程

1. 总管理任务从最新 `main` 建立 `codex/stage-<编号>-<主题>` 分支，先把新增产品裁决写入 `DECISIONS.md`。
2. 架构/合同先冻结；引擎与前端按不重叠目录并行；管理任务负责集成，不让多个任务共享写目录。
3. 完成专项、全量、静态、OpenAPI、真实浏览器和失败反向验证；测试数不得少于基线，skipped 必须为 0。
4. 独立审计失败后直接回原研发任务修复，再由同一审计任务复验，不等待用户逐步催促。
5. 通过后同步现役文档，提交、推送、开 PR、等待 CI、合并 `main`；没有进入 GitHub `main` 的阶段不算完成。

## 不随路线扩张的硬边界

- 独立创作不出现 AI 代写；作品拆解只分析作者正式正文。
- AI 辅助写作只维护一条正式正文，作者修改永远优先。
- `.env`、`.novel_*`、审计现场、真实作者数据和受版权保护的原文语料不进入 GitHub。
- 不把固定热门模板强套到所有小说；事实、推断和不确定性分开，重要结论必须能回到来源证据。
- 正式支付、管理员、多人协作、公开分享、云同步和生产部署均需另行决策。
