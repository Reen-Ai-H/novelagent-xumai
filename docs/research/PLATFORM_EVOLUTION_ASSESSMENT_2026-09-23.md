# 叙脉走向完整平台：架构评估与交付路线

评估日期：2026-09-23。性质：技术与产品建议，不替代已确认产品决定，不代表开始重构或批准生产发布。

## 结论

叙脉需要有针对性的架构演进，当前没有证据支持推倒重写。保留 FastAPI、Pydantic、现有模型运行时、正文版本和证据合同；围绕实际长篇样例，依次解决分支整合、增量分析、知识来源与时间边界、费用核算、编辑连续性。数据库迁移、前端框架替换和新的 Agent 平台暂不作为前置任务。

完整平台的目标应当是：作者可以持续写作、可靠保存和恢复，系统能解释作品中的人物与事件，AI 辅助路径能利用正确范围的作品资料连续创作，作者介入后能安全续接。支付、运营后台和公网部署属于后续商业发布层，不应成为验证这些核心价值的先决条件。

最大风险有两个。其一，最新体验方向和最新主线工程保障分别在两条分支上；其二，功能、结构校验与文学效果容易被混为一谈。增加字段、通过测试、读完所有章节，都不能单独证明“理解了全书”或“写得更好”。

主线 `deconstruction_depth.py` 明确采用规则与启发式。它适合提供可复跑结构、来源校验和保守基线，不能因六视角都有输出就认定文学理解成熟。PR #8 的模型报告能给出更丰富解释，但它仍有语义质量和整书收口待办。两者可共享证据与安全基础，不必把所有旧分析算法都作为新产品的必用引擎。

我的判断是，叙脉最值得验证的差异在于自动整理中文长篇，并让作者用较少纠错时间得到可信、能回证据的理解。单独增加人物卡、生成按钮或多 Agent 数量，难以证明这一差异。产品核心指标应包含“获得一份可信结果需要作者花多久”，而不只统计分析条数。

## 4. 是否重构：分项裁决

### 4.1 先整合工程基线，这是当前最高优先级

主线和 PR #8 都修改了 `deconstruction_service.py`、拆解 schema、前端及产品文档。直接用其中一条覆盖另一条，会有丢失安全保障或丢失最新体验方向的风险。测试数 204 与 161 的差别来自不同历史，不能据此指控候选删测试，也不能把较少测试的绿灯当作覆盖主线。

建议在独立集成分支上，先形成变更对应表，保留主线来源/CAS、项目锁、旧证据只读、隔离配置测试；迁入 PR #8 的模型报告与已认可展示、卷级结果、人物聚合和预算能力。模型报告与旧 2.0 报告之间使用显式适配边界，旧结果保留为只读兼容数据。阶段 33 只接纳与最新页面一致的必要体验修复。

不得把“按保留双方文件数算合并完成”作为验收。要重新跑正文修改后分析失效、历史证据、重建、重启、跨账户、并发发布与前端真实流程。报告本次没有执行集成，也不声称集成结果能通过。

### 4.2 应改全书分析的数据流，避免每段重写累计报告

PR #8 `book_analysis.py:124–182` 每段发送 `accumulated_analysis`，要求模型返回完整累计结果，并约束旧人物和事件 ID 不能消失；每三段增加一次记忆调用。最终以读完分段将任务标为 completed。这里没有独立的全书综合验收步骤。

若每段新增资料约为 d，n 段反复传入的历史资料体积接近 `d × n(n−1)/2`，这是在新增量稳定时的理想化估算，不是实测 token 或费用。它解释了为何更换数据库不能消除重复输入，固定输出上限也可能迫使后期结果越来越压缩。

先用样例证明需要保留哪些内容，再最小化修改现有 runner：每段返回新增、修正、失效声明和证据；程序合并稳定对象；必要时定向补读；全书完成时对主要人物、因果、核心线索和节奏进行一次有范围的综合。完整人物卡由这些结果形成，不要求每段重新写所有卡片。

卷级指纹与正文版本继续复用。当前有效卷集合及各自指纹组成全书综合来源清单，任一相关卷变化使对应综合过期。只追加不影响旧卷内容的章节时保留旧卷结果，但全书综合必须说明尚未纳入新章。

这项改动应在同源样例被认可后实施，符合最新“先内容、再最小集成”的顺序。

### 4.3 应补作品知识的语义边界，不必先建设知识库平台

主线 `MemoryItem` 有 project 和 chapter 字段，没有统一的稿本版本、读者可知范围或人物知情集合。`JsonMemoryStore.search()` 使用章节距离加分，没有将未来章排除。本次隔离诊断插入第 100 章资料，再以第 3 章查询，确实返回第 100 章资料。

这个结果只证明该检索函数不能独立承担时间隔离，不证明所有现役 AI 路径已经把未来信息发给角色，也不否定既有私有记忆测试。下一轮接入前必须追踪具体调用链。

建议将下列语义补进任务实际使用的对象与取材函数，初期可以是少量字段和普通函数，不建设独立上下文框架：

| 信息 | 必要含义 |
| --- | --- |
| 来源 | 作品、稿本、卷/章节、内容指纹及 evidence ID |
| 判断状态 | 正文明确事实、角色说法/传闻、推断、未知；不能把推断自动晋升为设定 |
| 生效与揭示 | 故事中何时发生，读者何时得知；无法确定故事顺序时保留未知 |
| 可见范围 | 任务允许阅读到哪里，当前角色知道什么；全书分析与角色推演的权限不同 |
| 修正记录 | 哪个判断被替代，依据是什么；不抹掉旧阶段的认识 |

执行顺序必须是授权与来源/范围过滤 → 定向取材 → 排序与预算裁剪。向量或关键词相似度不负责判断访问资格。人物身份模糊时允许保留未归属提及；提到地点不等于到访。

一个容易理解的验收场景是：第 3 章角色相信某人死亡，第 60 章揭示是假死。全书导读可以解释整个设计；第 3 章的读者视图与角色续写上下文不能提前包含第 60 章真相。这里需要正确的资料边界，单靠提示词“不要剧透”不够。

### 4.4 应补预算边界，暂时不能承诺 70 万字 ≤10 元

候选 `model_budget.py` 已有预检和预留额，值得复用。但存在可直接验证的缺口：`record()` 在 usage 未知时只增加 unknown 计数，不增加花费或保留占用。本次用 100 次未知用量的合成返回调用它，累计花费仍为 0，下一次预检仍允许。

这不证明实际账单已经超支，但说明目前的预算门不能覆盖供应商未返回用量的情况。请求前的字符估算也不应未经标定就称为保证性的 token 上界。代码的静态价格版本不能当作今天的报价，本报告不据此计算真实模型价格。

建议沿用同一账本，增加请求前额度占用、成功后实际结算、未知费用保守保留或暂停、逐 attempt 记录、重复回执去重以及重启恢复。调用明细应持久化安全元数据；当前 runner 保存的是 `ledger.public()` 汇总，进程内 records 不等于持久账。每次调用应能追到模型、价格版本、阶段、输入/输出/缓存用量、费用是否已知和重试身份，不保存 prompt 或私有记忆。

费用实验分别报告“从零拆整书”和“复用旧结果补全”，全流程包括分段、补读、记忆、综合、结构修复及重试。若 10 元内质量不足，应报告实际范围和差距，再选择调整模型、处理量或预算；不能少做综合却宣称达到目标。

### 4.5 前后端应逐步拆模块，但不把换框架当成果

主线实测文件规模：`frontend/app.js` 3,367 行、`ai_service.py` 2,733 行、`deconstruction_depth.py` 1,794 行、`independent_service.py` 1,654 行、`deconstruction_service.py` 1,527 行。行数本身不是缺陷；与全局 state、混合编排/持久化/公开投影一起看，说明功能相邻改动容易牵动其他流程。

前端优先沿编辑会话、保存状态、档案/版本、拆解展示、导演运行拆出模块，保留 API adapter；让离页 flush、旧响应失效和加载/销毁职责清晰。只有实际交互复杂度与维护成本证明需要时，再评估 TypeScript 或组件框架，不在当前阶段整站迁移。

后端在修改相关流程时，逐步将模型调用、分析合并、公开投影和持久事务拆成可测试单元。保留当前 routes → service → store 层次及 API 兼容。新接口优先通过公开方法协作，减少候选 runner 对 service/store 私有方法的依赖。

### 4.6 存储和任务调度按测量结果演进

`IndependentStore` 以作品为粒度整份解析、序列化和原子替换；main 的 AI/拆解 worker 定期扫描记录，AI worker 还会逐任务等待执行。已有文件锁、journal、outbox 和恢复机制不能被忽略，也不需要重新造一套恢复平台。

这些实现存在大作品反复写盘、全量扫描和任务等待时间随负载增长的风险，但本次没有做容量压测，不能直接判定“目前已经慢”或“某个用户数必然撑不住”。

先测 100 章、约 70 万字及多个并行测试作品的保存延迟、内存、扫描耗时和任务等待。若记录规模造成瓶颈，先抽 repository 边界、按章/对象读取，再评估 SQLite 单机事务存储；只有确定需要多实例或更多并发写入时，才评估 PostgreSQL 与独立 worker。图数据库、向量服务不属于当前必需设施。

任务最小完善项是稳定身份、来源版本、进度、可恢复检查点、失败/取消状态及预算引用。若要多进程运行，再补持久领取、租约与过期恢复。跨进程避免重复提交与供应商计费恰好一次是不同问题，后者不能只靠本地锁承诺。

若以后迁移存储，先对隔离副本演练，新旧读结果核对、正文逐章 hash 校验、版本/证据核对和回滚均通过后才制定用户迁移方案；不在启动时自动批量改写 `.novel_*`。

## 5. 目标架构：一个模块化应用，共用正文与知识基础

```text
独立写作工作区                     AI 创作室 / 导演台
        │                                  │
        └──────── API 与作者权限 ────────────┘
                           │
           正文与稿本服务（唯一正式正文）
                  │                  ↑
       来源绑定的章/卷分析          作者优先的正式提交
                  ↓                  │
       知识声明、证据、阶段变化 ─→ 按任务取材 ─→ 生成/审查
                  │
        作者阅读视图 / 全书综合

共用基础：模型运行时、持久任务、预算账、版本门禁、日志与恢复
```

这是演进后的职责划分，不要求建立多个服务。展示视图、模型输入和证据历史引用相同对象，但具有不同投影和可见范围。分析结果始终是派生资料，作者正文是权威来源；生成中的候选内容只有经既有正式提交流程才成为新事实。

地点与场景作为解释人物、事件所需的轻量关联即可。先挂在现有大剧情下，不强制独立场景库或地点工作区。作者应看到“谁为什么这样做、事件如何相连、依据在哪里”，无需理解内部任务和模型链。

## 6. 从现在到完整平台的路线

以下使用交付里程碑而非占用既有阶段编号。近一步具体，远期以进入条件约束，避免重新形成必须全部建设的大清单。

| 里程碑 | 作者能获得什么 | 主要工作与复用 | 通过条件 / 停止条件 |
| --- | --- | --- | --- |
| M0：统一可继续开发的基线 | 下一轮工作不会因分支差异退回旧体验或旧保障 | 汇总 main、PR #8 与阶段 33；记录最新范围，分块集成，修复干净环境测试 | 集成回归与来源/正文安全通过；不把合并本身算内容质量完成 |
| M1：内容样例达标 | 看懂 1–2 位人物、2–3 个相连事件、一条前后完整线索 | 复用已认可章节结果，只补读缺口；先交可读样例 | 作者认可理解价值，关键判断能回证据；不为配角和字段齐全延长阶段 |
| M2：可用的整书拆解 | 能浏览全书主要人物、主线与暗线、必要节奏，知道范围和费用 | 增量提取、针对性修正、全书综合、完整预算、来源失效；保持现有页面 | 前中后抽查通过，正文读取和全书综合分别标状态，受控成本试验有完整账 |
| M3：可靠的长期写作工作台 | 写、存、完成章、看档案、改旧章、恢复版本可以连续完成 | 选择性接入阶段 33；保存状态、定位、批次确认、完整预览与恢复 | 真实 100 章工作流、失败与重启恢复、历史只读、键盘和目标视口通过 |
| M4：有证据的 AI 质量提升 | 利用作品资料生成连续章节，关键事实与人物动机更稳定 | 在重新开启生成范围后，用现有 runtime 做任务取材与小样对照；仅补证实有效的方法 | 同模型、同蓝图对照；硬事实错误、人工修改负担和盲评有实际改善 |
| M5：作者可随时介入的连续写作 | 暂停、改稿、恢复后能接着正确版本继续 | 暂停/失效旧生成、更新相关资料、重组上下文、复用正式提交事务 | 作者改稿不被旧任务覆盖；新章节沿新事实继续；取消、重启与并发行为明确 |
| M6：完整开发版发布准备 | 两条路径可长期使用，并有可验证的备份和恢复方式 | 跨平台回归、真实作者试用、容量测量、依赖与运维文档；按需做存储/任务演进 | 数据恢复演练、核心质量与费用门、使用体验全部有证据；不等同于公网发布 |
| M7：商业在线平台，可选 | 跨设备正式服务与受控运营 | 单独确定身份、托管、租户隔离、计费、运维职责和预算 | 独立产品与安全决策后执行；当前未授权实施 |

M0 的准备与 M1 的内容评估可以并行，但最终集成结果必须在统一基线上验证。M3 中直接阻塞 M1/M2 使用的小修可以提前，不必等整本分析完成。M4 不以先训练模型、蒸馏或建设双引擎为条件。

若生成质量不足，先做失败归因：资料没选对、角色知道了不该知道的事、场景目标不清、篇章计划不稳、模型表达能力不足，各自需要不同修复。只有对照证明某种类型规则或表达策略有效，才将它固化为模块。不要一次更换模型、prompt、存储和 UI，否则很难判断提升来自哪里。

M5 的具体流程应是：作者开始介入 → 旧生成失去提交资格 → 保存新的作者 revision → 标记受影响资料过期 → 增量更新 → 从新来源生成 → 正式提交。涉及重大设定冲突才询问作者；通常的修辞修改不应让作者面对内部流水线。

目前无法负责任地给出完整平台的固定完成日期：整书内容和连续生成效果尚未通过真实质量门，且分支集成成本未实测。建议每个里程碑以可运行结果和退出条件交付，M1/M2 得出内容与费用数据后再估下一段排期。

## 7. 怎么验收“达到预想功能和效果”

功能、内容、安全、成本分别评价，任何一项不能用另一项替代。以下新增量化阈值是建议起点，正式实施时应写入验收合同；不是本次已经达到的指标。

### 7.1 拆解内容与作者价值

同源前后对照使用一份已认可材料，加一份经授权、较少见的原创材料，降低模型凭熟悉作品知识补答案的干扰。主样例覆盖人物选择、关系变化、因果、线索揭示及相应证据；全书抽查覆盖前、中、后与远距离关联。

关键正文事实、证据错绑、主要人物错误合并采用零容忍；解释性的动机与节奏允许明确的不确定性，不要求全书每一句都被分析。初始可人工标注 30–50 项关键判断，建议将可判定事实支持率 ≥95% 作为试跑目标，同时单列覆盖率和严重错误，防止靠大量“未知”提高准确率。文学判断另由作者评阅，不把这个比例叫作文学质量分。

邀请 3–5 位目标作者做形成性试用，记录寻找一条线索所需时间、每轮纠错次数、得到可信人物卡所需分钟数，以及一周内是否继续使用。这个规模适合找问题，不足以证明市场需求或付费转化。

### 7.2 生成效果

从现有模型+简明任务的基线开始，再加入经过验证的作品资料，同一设定和模型至少比较数个连续章节片段；作者修改后续写单独测。逐步扩大到 10–20 章观察远距离设定与节奏，不以三章链路能运行证明长篇文学质量。

盲评关注人物选择是否可信、因果是否成立、语言是否重复、场景是否推动故事；程序关注硬事实违背、角色私密信息越界、错误版本引用、作者修改丢失。记录生成后人工修改时间和实际费用。没有证明增益就不引入更多模块。

### 7.3 性能与可恢复性

建议先在声明的测试机器、数据量和网络条件下建立基线：100 章及约 70 万字合成作品，分别测试单作品和多个并行作品。候选体验目标可设自动保存完成 p95 ≤1 秒、章节打开 p95 ≤1 秒；正文安全与失败缓冲独立验证。这些数字是建议目标，本次没有测出对应性能。

测试保存网络失败、revision 冲突、分析中服务重启、生成返回后提交前崩溃、预算耗尽与恢复、版本恢复取消和重复确认。必须逐字或 hash 核对正文，而不是只检查 HTTP 200。

### 7.4 费用

全流程成本采用 `Σ(未缓存输入 × 对应价格 + 缓存输入 × 对应价格 + 输出 × 对应价格)`，统一单位并包含每次实际 attempt。未知用量单列为未结算，不按零元计算。价格需要在真正试验时核验并冻结，不能复用过期报价。

先小样，再包含远距离线索的中样，最后整书。每一轮同时报告完成范围、质量、总花费与剩余预算。约 70 万字 ≤10 元保持为待验证目标，不能用理论估算或利用旧结果的补全费用认证。

## 9. 下一轮应交付什么

下一轮最有价值的结果是一个能在现有页面核对的同源内容样例，同时完成集成基线准备。样例呈现主要人物的选择与变化、少量相连的大事件、完整核心线索和必要节奏；记录旧结果哪里已足够、哪里需补读。用这个结果决定最小增量合同，随后才改 runner 和费用边界。

报告中的存储迁移、模块拆分、质量实验及商业发布均按各自触发条件推进。任何时候，只要当前方案已经满足内容、使用、安全和成本门，就可以结束该里程碑，不必为了架构完整补齐所有候选设施。

最终值得交付的平台，是作者能放心保存和持续创作、系统能可靠记住并解释作品、AI 能沿作者意图继续写作的工具。架构的价值应通过这些行为与实测结果体现。
