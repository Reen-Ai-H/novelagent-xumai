# 叙脉产品决定记录

本文件记录已经拍板的稳定决定，不记录每次讨论过程。新决定若替代旧决定，要直接标明替代关系，并同步更新产品规格、交互和验收。

## 2026-08-10 · 首版产品基线

### 品牌与方向

- 产品名确定为“叙脉”。
- 唯一小标语确定为“新一代写作体验”。
- 首版以前端原型 A“故事档案室”为主；A 的首页最佳，整体最均衡。
- B“夜航排演室”和 C“未来活字”保留为后续局部视觉灵感，不作为首版实现基准。

### 产品结构

- 保留两条入口，名称固定为“独立创作”和“AI 辅助写作”。
- 首版核心页面确定为：产品首页、登录、书架/新建作品、独立编辑器、故事档案、AI 创作室、AI 导演台。
- 独立创作没有 AI 导演台；AI 辅助写作同时有导演台、编辑正文和故事档案。

### 独立创作

- 接受“首次全量导入，之后逐章追加”的长期项目模式。
- 网页是主要载体，正文和状态需要服务端保存并支持多端继续。
- 接受“写作时安静，章末集中检查”。
- 点击完成本章后更新角色状态、剧情线、伏笔、疑问点和快照。
- OOC、冲突、重复、矛盾不直接判错，统一进入低压力的“疑问点”。
- 接受“确定内容自动更新、随时可撤销；不确定内容进入疑问点”。
- 档案默认显示最新状态，并可切换到任意章节查看当时快照。

### 修改与版本

- 修改旧章不创建新作品，而是在同一作品内创建新稿本版本并从头分析。
- 旧分析立即替换；旧正文保留 30 天可恢复。
- 编辑过程只保存待确认修改；作者主动点击“确认全部修改”才结算，不按每字或每章生成版本。
- 系统展示修改范围并提出建议，但作者始终最终选择“忽略轻微措辞修改并继续”或“根据当前全文重建档案后继续”。
- 独立创作和 AI 辅助作品共用这一修改逻辑。

### 角色图片

- 首版纳入可选 AI 角色试绘。
- 首次分析只自动分配内置非具象角色牌，不消耗积分，不提前固定外貌。
- 作者选完画风后按需生成具体角色，不自动生成全员插画。

### 后台任务

- 接受“后台分析、可离开页面、完成后通知”，不要求作者停留在等待页。

### AI 辅助写作

- 作者先与一个统一“主编”讨论并补全蓝图，后台专业角色不轮流占据聊天界面。
- 确认蓝图后，AI 可以自行轮转完成角色推演、正文生成、审查与档案更新，不要求作者逐段审核。
- 每个故事角色拥有私有记忆；角色之间不共享私有记忆，但共享世界观及必须知道的事实。
- 作者以“导演”方式在关键节点选择少量选项。
- 不同时维护多条平行正文；选择后继续唯一正式正文。
- “提前展示可能后果”放在设置，默认关闭。

### 账户与后台

- 首版先完成邮箱登录；手机号、微信页面预留但不真正实现。
- 未来正式发布前建设管理员平台：查看账户、创作积分、模型 token/成本，创建账户并充值。
- 管理员功能不属于当前首版实现。

### 暂不做

- 分享、公开发布、一键投稿、隐私中心等外围页面。
- 平行正文、分支树长期维护。
- 自动全员插画。
- 原生移动端、真实支付、手机号/微信真实登录。

## 变更规则

新智能体不得自行推翻以上决定。如果代码实现需要偏离，先把原因和影响写入根目录 `BLOCKED.md`，由产品讨论形成新决定后再更新这里。

## 2026-08-11 · commit marker 后作者 revision 并发收敛

- 作者正文永远优先。导演事务在持久化 commit marker 时记录稿本 revision；marker 后发现作者 revision 漂移时，AI 不得覆盖作者正文。
- 所有会改变 active version、章节 revision 或 pending changes 的作者写入口，都必须先与同作品未终结的导演事务使用持久、跨进程的项目写锁串行化；不能安全先完成事务时，返回明确可重试的作者修改冲突。
- 若 marker 后已有外部旧代码写出更高 revision，系统只在能证明无冲突并保留作者内容时幂等完成；否则把事务持久收敛为 `author_revision_conflict`/superseded：作者 revision 保留，AI run 为失败可重试，AI 正式章、快照和完成通知不可见，不扣开发积分，安全 usage 元数据保留。
- 跨 store 事务使用 durable journal 的补偿状态和 commit marker。补偿可在启动、worker、公开读取、选择和重试入口重复执行；未达到终态时公开入口以同一作者优先视图返回，不抛 `IndependentServiceError` 或 500。旧事务无补偿字段时继续按已有 payload 兼容恢复。
- 冲突后的重试创建新的事务/幂等键，旧事务不得复活或重复投影；普通选择仍记录 `author`，把决定交给角色及 worker 恢复仍记录 `character`。

## 2026-08-14 · AI 蓝图同步与信息架构反馈（待研发）

- 现象记录：作者在 AI 创作室发送第二轮补充后，主编对话会保存并正常显示，但右侧蓝图可能仍停留在上一版。当前根因不是浏览器刷新失败，而是主编提示与服务端合并策略都把模型产出限定为“只补充作者尚未明确的字段”；`_apply_model_blueprint_patch` 对已有非空字段不覆盖，因此新的人物名、城市风貌、域外生态等细节只进入对话，不会更新已有字段。
- 产品反馈：作者认为当前右侧九字段连续表单观感较差、信息密度高且缺少故事结构感。后续研发需将蓝图改为更易浏览的卡片式信息架构，至少包括人物卡、世界观/设定卡、主冲突与剧情线卡，并保留作者可直接编辑、版本与冲突保护。
- 剧情线方向：剧情线不应只作为一个长文本输入框；应支持点开进入独立的完整剧情线页面，以章节/节点/人物关系组织推进、选择与来源。视觉参考《底特律：化身为人》的剧情线/关系图体验，但不复制其视觉资产或交互细节。
- 同步语义待定：后续需明确“主编建议更新”与“作者已确认字段”的优先级。建议采用可审阅的字段变更建议（新增、替换、合并、待确认），由作者确认后写入蓝图；在此决定落地前，不改变现有只补空字段的安全策略。
- 范围声明：本条仅记录用户反馈和后续产品方向，本轮不修改前端、蓝图 API、数据模型或现有作品数据。

## 2026-08-14 · AI 主编长程工作流与流式交互反馈（待研发）

- 现象记录：当前主编每轮回复较短，等待一段时间后一次性完整出现；作者感知不到持续生成过程，也感到系统过快给出结论、蓝图和方向，缺少长程思考与质量检查。
- 技术根因：现有 `/messages` 只发起一次 `blueprint_editor` 结构化调用，运行时使用非流式 JSON 合同（`streaming: false`），前端 `requestJson` 等待完整 HTTP 响应后才渲染；模型只被要求返回 `reply + blueprint_patch`，最大输出约束为 1600 tokens。无 Key 时则直接使用确定性短回复。
- 产品原则：不向作者暴露模型的隐藏思维链、私有提示或内部推理原文；“长程思考”应转化为作者可理解、可恢复、可审阅的工作阶段、依据、待确认问题和质量检查结果。
- 后续主编流程建议拆为持久阶段：理解本轮意图 → 提取事实/约束/未知项 → 必要追问 → 形成蓝图变更提案 → 检查人物/世界规则/冲突与时间线一致性 → 汇总待确认项 → 作者确认后写入蓝图。未完成质量门时，不自动把整套蓝图视为定稿。
- 后续交互建议：人类可读回复采用 SSE/流式增量展示；蓝图变更作为单独的严格结构化提案，在流结束后校验并展示新增、替换、合并和待确认差异。流式文本不能直接当作已保存蓝图。
- 后续质量建议：保留多轮会话摘要、已确认事实、开放问题、冲突检查结果和蓝图版本；让主编先追问关键缺口，再逐步确认，而不是每轮直接生成九项完整蓝图。专业角色应提供可见的短状态和检查产出，但不展示隐藏 prompt 或私有记忆。
- 范围声明：本条是产品反馈与后续研发方向，本轮不修改流式协议、提示词、模型调用或页面实现。

## 2026-08-14 · 蓝图生成可视化体验提案（待研发）

本条记录作者对“蓝图生成过程”的体验设想，属于待研发设计提案，不改变当前实现合同。

### 总体原则

- 蓝图生成不再只是右栏九个文本框突然出现，而应成为一段可观察、可暂停、可恢复的“故事结构成形”过程。
- 动效只能表现已经由服务端验证并持久化的产出，不能用预设动画假装模型已经完成，也不能把隐藏思维链、内部 prompt 或私有记忆展示给作者。
- 右栏保留摘要入口；完整蓝图进入独立工作台，人物、剧情线和世界观各有清晰的浏览层级。
- 每个内容单元带状态：作者已确认、主编建议、待作者确认、存在冲突。主编建议不能无提示覆盖作者已确认内容。

### 生成过程

建议将一次蓝图更新拆成可恢复阶段：

1. **收束本轮对话**：提取作者明确说出的事实、偏好、限制和新增方向。
2. **识别缺口与冲突**：标出还不清楚的地方，以及与既有蓝图可能不一致的内容。
3. **人物成形**：按人物逐个揭示姓名、身份、年龄、性格、动机和关键经历。
4. **剧情生长**：从起点向右绘制主干，再展开分支、节点、关系和阶段结果。
5. **世界展开**：先呈现整体世界/星球，再缩放到城市、郊区、域外和关键地点，补充环境与风俗。
6. **一致性检查**：检查人物动机、剧情因果、世界规则、时间线和关系变化。
7. **变更提案**：展示新增、替换、合并、冲突和仍需作者决定的内容，作者确认后才写入蓝图版本。

### 三类核心动效

- **人物卡**：卡片先出现非具象角色牌，再按真实产出逐项填入姓名、年龄、性格、欲望/恐惧和经历；新增或变化字段短暂标记“本轮建议”，不使用夸张打字机效果掩盖事实来源。人物经历可在卡片内展开为从童年到当前故事时点的时间轴。
- **剧情线工作台**：参考《底特律：化身为人》的“关系与节点逐步展开”感受，但不复制其资产。左侧为故事起点，主干向右生长；分支从节点展开，节点可表示事件、选择、人物关系、线索和未决问题。点击节点打开完整详情，显示来源、前置条件、影响人物和确认状态。
- **世界观地图**：先展示一个克制的世界/星球轮廓，再以四个方向区域逐步揭示森林、城市、郊区、域外等结构；缩放后显示地点、生态、城市风貌、习俗和资源。地图只是结构化浏览，不把尚未确定的内容渲染成确定事实。

### 交互与质量门

- 左侧主编对话继续负责讨论；右侧先显示生成进度与摘要卡，点击“展开蓝图”进入完整工作台。
- 生成过程中可以暂停、继续、跳过动效但不能跳过服务端校验；刷新或离页后从持久阶段恢复。
- 每轮优先生成“变更提案”，而不是直接生成一整套九字段蓝图。作者可以逐条接受、全部接受或忽略；冲突字段必须单独处理。
- 如果关键缺口会影响主线，主编先追问少量高影响问题，不急于填满字段。未确定信息进入“待确认/疑问点”，不被包装成完整结论。
- 流式协议建议只传递可公开事件：阶段开始、人物卡片字段、剧情节点、地图区域、检查结果、提案完成和等待确认；结构化事件必须逐条校验后才能渲染为可信内容。

### 动效边界

- 不人为延长等待时间；动效跟随真实事件到达，模型较快时允许自然快速完成。
- 提供“跳过生成动画”和“减少动效”选项；遵守 `prefers-reduced-motion`，改为即时显示、淡入和明确状态文字。
- 动效失败、连接中断或模型失败时，保留已确认内容和已通过校验的增量，明确显示下一步，不显示虚假的完成状态。
- 目标是“让作者看见故事怎样被组织”，不是让作者观看模型的隐藏推理过程。

### 范围声明

本提案暂不修改前端、流式 API、数据模型或现有作品；后续若进入研发，需先补齐交互原型、事件合同、蓝图提案数据模型和视觉验收标准。

## 2026-08-14 · AI 正文编辑器与章节质量反馈（待研发）

### 编辑器信息架构问题

- 现象记录：正文编辑页右侧人物卡目前把主角姓名、角色、目标、已知事实、情绪和当前场景等信息以零散摘要堆叠展示，视觉上像未整理的字段集合，不能让作者快速理解“这个人物是谁、现在处于什么状态、为什么重要”。
- 优化方向：人物应使用结构化人物卡，至少分为姓名/身份、核心性格、当前目标、关键关系、当前状态和来源章节；长经历折叠到时间轴或详情页，默认只展示少量高价值信息。AI 私有记忆不能出现在浏览器人物卡中。

### 主要剧情信息过载

- 现象记录：正文页下方或右侧“主要剧情”目前文本过长、层级不清，信息很多但难以阅读和定位。
- 优化方向：默认展示一句话主线、当前章节节点、下一步悬念和最多几条关键线索；完整剧情进入可展开的独立剧情线页面，以节点、分支、人物关系和来源章节组织。避免把整段大纲直接压成一个长文本框。

### 标题提取与章节标题

- 现象记录：当前生成/编辑后的章节标题没有稳定从正文或导演产出中提取出来，页面出现未命名或不符合内容的标题。
- 待研发合同：章节标题必须是服务端持久字段，来源明确区分“作者提供”“模型建议”“系统默认”；模型未给出合格标题时不能假装提取成功，应显示待命名并允许作者编辑。标题变更需要保留版本与冲突保护。

### 单章字数不足

- 现象记录：当前 AI 生成章节经常只有约 1000 多字，与作者期待的长篇章节体量不一致。
- 可能根因方向：当前正文阶段存在 1200–2000 可见字符的基础合同，但这只是接口下限/上限，不等同于完整章节目标；实际输出还受模型 token、上下文、输出校验和当前生成策略影响。需要后续单独定义目标章节长度、段落结构、场景完整度和章节结尾合同，不能只把 max_tokens 调大。
- 待研发方向：在蓝图和导演台中明确章节目标字数或场景目标；生成后做长度、场景闭合、人物动作、冲突推进和结尾钩子的质量检查。失败时重写或进入可重试状态，不用截断、拼接模板或虚报字数。

### 语言与小说质量专项

- 现象记录：当前正文存在语言表达、节奏、自然度和文学完成度仍需调整的问题。
- 产品边界：后续将把小说质量作为独立研发/评测方向，单独建立脱敏样本、评价标准、真实生成对比和回归证据；功能审计通过不等于文学质量通过。当前离线质量门研究 Q2 已验证，但真实生成质量增益与产品集成仍 pending。
- 本条范围：本轮只记录问题与研发边界，不修改现有正文、标题、档案数据或编辑器实现。

## 2026-09-04 · 独立创作与作品拆解 V1.5（阶段 31）

- 作品拆解位于“独立创作”内部，不新增首页第三条产品路径；工作区导航由正文、作品拆解、故事档案、版本记录组成。AI 辅助写作沿用现有路径，本阶段不重做 AI 创作室或导演台。
- 成熟成品导入与在写作品共用独立作品、稿本、账户归属和导入预览/确认合同。导入确认后自动排队拆解；空白作品必须有至少一章已完成正文后才有足够材料。
- 拆解是绑定 `account_id + project_id + active manuscript version + source revision/hash` 的版本化派生数据，单独保存在 `.novel_deconstruction`，不回写或迁移已有 `.novel_independent`、`.novel_projects` 等数据。
- 首个纵向切片包含作品概览、基于实际正文章节/片段的 0–100% 节奏时间线、章节拆解表和 evidence back-link。每条重要判断带来源章节/字符范围、最小摘录、confidence 与 uncertainty；不确定内容不得冒充事实。
- 后台拆解状态持久化为 `queued → running → completed` 或 `failed_retryable`；正文来源发生变化时显示 `rebuild_required`，作者主动重建，不依赖前端定时器推进。服务启动、公开读取和手动重试都能恢复/幂等。
- 无模型路径使用明确的“确定性结构拆解（无模型）”标签；本阶段不调用真实模型、不把用户上传内容贡献给公共类型引擎。人物弧、完整剧情线关系图、读者体验曲线和文笔技法深挖列为阶段 32+。

## 2026-09-04 · 作品拆解后端架构收敛（阶段 31B）

- 作品拆解采用正文侧车中的 durable outbox：正文/稿本写入与拆解触发事件同一次安全原子保存；派发失败只留下可重试事件，不把已保存正文转成接口 500。服务启动、后台 worker、拆解读取和重试入口都可幂等补派。
- 锁顺序固定为“作者/项目写门禁 → 正文侧车写入”；拆解服务读取正文时不持拆解锁，完成或失败只在短窗口持拆解锁；确认 outbox 事件必须在释放拆解锁后再进入作者写门禁，禁止 `deconstruction → independent` 反向嵌套。
- 拆解异常统一持久为 `failed_retryable`，不把异常原文、正文或内部材料写入侧车或公开响应；单个损坏侧车不能阻断其他作品的 worker 恢复。
- 证据定位绑定 `document_id`、稿本版本、来源 revision/hash，并以 `utf16_code_unit` 表示正文偏移。来源不再是当前稿本时只返回历史只读定位，不跳转到当前同编号章节。
- 四个拆解接口使用严格公开 response model。`effective_status` 是用户应采取动作的唯一主状态；`run_status` 描述当前/最近运行，`source_match` 描述结果是否绑定当前正文；只有三者满足当前来源且运行完成时才返回 `result`，兼容旧字段必须与 canonical state 同步。

## 2026-09-05 · 独立创作连续写作合同（阶段 33）

- 阶段 33 只收口独立创作现有的正文、章末处理、故事档案、版本记录和作品拆解，不新增 AI 代写、分享、协作、云同步、支付或生产能力；默认不新增公开 API 和持久字段，只有黑盒验收证明现有合同无法安全完成时才允许后端扩展。
- 当前章节身份进入 URL 查询参数。有效的显式 `chapter` 优先；没有有效参数时，先选择编号最大的未完成章节，否则选择最后一章。章节切换、新建章节以及正文、档案、拆解之间往返必须保留该参数；不用 localStorage、sessionStorage 或新的账户画像保存阅读轨迹。
- 新建章节成功后立即进入新章并把焦点交给章节标题。已完成且正文未修改的章节不能重复提交“完成本章”，主操作改为“新建下一章”；旧章修改后才重新进入可完成状态。后台超时、刷新和重登仍从服务端真状态恢复。
- “已保存”只表示当前标题和正文已经按 revision 落盘，与章节是否完成、档案是否分析完成分开。正在保存、本地待保存、保存失败和 revision 冲突必须用不同状态表达，不能因章节仍为写作中而把已落盘内容显示为“等待保存”。
- 版本预览必须允许逐章查看目标稿本，不只截取第一章；恢复是明确的两步动作，先选目标并预览，再二次确认。恢复继续由服务端创建新的当前稿本，历史稿本只读，作者正文不被就地覆盖。
- 旧章修改决策同时说明故事档案与作品拆解的影响。选择全文重建后，两类派生结果都按当前正式正文恢复；选择忽略只保留现有派生结果，不把旧结果伪装成已重新分析。
- 本合同以 `goals/STAGE_33_INDEPENDENT_EXPERIENCE.md` 的真实浏览器流程和反作弊门禁验收。功能任务通过后仍须由未参与实现的可见 Luna/max 任务独立审计，P0/P1/P2 均为 0 才能合并。
